# GeoClar 影像检索与选景

按固定顺序调用工具，每一步都先看返回再决定下一步。**不要跳步，也不要在失败后连发重试。**

## 一、先把用户给的位置变成范围（WKT）

所有工具的范围入参都是 WKT，而**平台不提供地名解析**（没有地理编码工具）。用户说位置有三种情形：

- **给了文件（KML / KMZ / SHP / GeoJSON）** —— 由你（助手侧）读成 WKT。后端不接收文件、也不解析几何。
- **给了坐标串** —— 直接用；先确认是 WGS84 经纬度，别的坐标系要先转换。
- **只报了地名**（"北京朝阳区""上海浦东"）—— 你可以按自己的地理知识给出**近似**范围，但必须：
  1. 在回复里**明确标注"这是我按地理知识估的近似范围"**，写出你理解的地名与大致边界；
  2. **等用户确认之后再往下走**。不要拿一个未被确认的近似范围直接去检索 —— 一次检索会真的并发打多个数据源，范围估错，整轮结论和金额都偏。

## 二、调用顺序

1. **`geoclar_list_datasets`** —— 看平台有哪些已发布数据集（分辨率、传感器、计价单位）。
   这是**平台公开目录**，出参 `visibility=public`，**不按客户过滤**：不要读成"这个用户被授权的数据集"。
   客户授权不足的表现是**检索命中偏少或为空**，全程不报错。
2. **`geoclar_inspect_aoi`（WKT）** —— 检索前先体检。
   - **可以直接检索的判据**：`rules` 六条**全部 `pass === true`**，且 `regularization.unavailableReason === null`。
     `pass === null` 是"本期无法判定"，**不等于通过**。
   - 不满足就**先别检索**：把结论讲给用户（面积账、碎片、问题码），并给出规整矩形 ——
     `rotatedRectWkt`（更省）与 `axisAlignedRectWkt`（正南北、不会被拒）**两个都给**，用 `costRatioRotated` / `costRatioAxisAligned` 讲清代价比（`rotatedAccepted=false` 表示旋转版会被拒），等他确认用哪个再进下一步。
3. **`geoclar_search_scenes`（WKT + 云量/时相/数据集）** —— 看返回值里的 `mode`：
   - `mode=direct`：本次已同步返回结果摘要，进第 5 步汇报。
   - `mode=task` + `taskId`：范围大，后端把它拆成异步任务了。**用 `geoclar_get_search_result(taskId)` 取，不要重发检索。**
   - 注意：本工具**没有分辨率入参**。"只要优于 N 米"这类要求去第 5 步的方案推荐里用 `maxGsd` 表达。
4. **`geoclar_get_search_result`（taskId）** —— 进度与结果。任务在跑就如实说"还在跑"，等一会儿再查；同时可以继续和用户讨论别的（改条件、看别的区域），不必阻塞。
5. **`geoclar_recommend_schemes`（WKT + 条件）** —— 要**方案取舍**或**金额**时才调。

**检索结果怎么读**（两个检索工具同一形状）：

- `returnedCount` 是**后端本次可得的条数**（受落库上限约束），**不是发给你的条数**；任务分支另有 `totalResults` = 命中总数。
  **发给你的 `scenes` 恒定最多 20 条** —— `truncated=true` 就表示超过 20、只给了前 20。
  所以不要把 `returnedCount` 说成"共找到 N 景"：它是"后端手里有多少"，不是"给到你多少"。
- `progress` 四个数恒等：`succeeded + failed + unfinished === chunkCount`。`failed > 0` 就说"部分批次失败"。
- 任务 `status` 的终态是 `success` / `partial` / `failed`；不是这三个就还在跑，继续等，不要下结论。
- `coverage` 是这次范围的 `regionAreaKm2` / `coveredAreaKm2` / `coveragePercent`。
- 每景只有四个标量：`id`、`acquiredAt`、`cloud`、`resolution` —— 完整几何与厂商字段一律不下发，不要去向用户承诺更多字段。

## 三、挑一套方案给用户

**一个条件都不给** = `mode=presets`，返回 **12 套**预设方案；**给了任一条件**（云量 / 时相 / 预算 / 分辨率 / 侧摆角 / 数据集 / 同期一致）
= `mode=custom`，返回 **4 套**：`CUSTOM`（按用户条件算出来的那一套，打头）+ `LATEST` / `SHARPEST` / `CHEAPEST` 三套**同池对照**。

对照与 `CUSTOM` 跑在**同一个筛后池、同一套档位**上，所以**可比** —— 用户问"这套贵不贵、清不清晰"，直接拿这三套比给他，不必自己另算一套。

`schemes[].key` 只有英文码，中文名按下表说（后端故意只出码，标签在门户侧）：

| key | 对用户怎么说 | key | 对用户怎么说 |
|---|---|---|---|
| `LATEST` | 时相最新 | `RECENT_SHARP` | 近期 · 兼顾清晰 |
| `SHARPEST` | 最清晰 | `RECENT_CLEAN` | 近期 · 兼顾干净 |
| `CLEAREST` | 云量最低 | `CLEAN_CHEAP` | 干净 · 兼顾省钱 |
| `CHEAPEST` | 最省 | `SHARP_CHEAP` | 清晰 · 兼顾省钱 |
| `SHARP_CLEAN` | 清晰 · 兼顾干净 | `VALUE` | 性价比 |
| `CLEAN_SHARP` | 干净 · 兼顾清晰 | `CONSISTENT` | 同期一致 |

`mode=custom` 时那一套的 `key` 是 `CUSTOM`，门户上叫「推荐方案」——不要把它混进上面 12 套里说。

**默认给一套为主，不倒一整张表**：`presets` 时以 `VALUE`（性价比）为主推荐、附 `CHEAPEST` 与 `SHARPEST` 做对照；
`custom` 时以 `CUSTOM` 为主，那三套对照**本来就在返回里**，直接用。用户说了偏好（"要最清楚的""越便宜越好"）就换成对应的那一套。

一套方案里能拿来谈取舍的就是这些字段：`sceneCount` 景数、`coveragePercent` / `coveredAreaKm2` / `uncoveredAreaKm2` 覆盖、
`dateFrom` / `dateTo` 时相、`gsdMin` / `gsdMax` 清晰度、`cloudCoverMax` / `cloudCoverMean` 云量、`estimatedAmount` 金额。
另有 `scenes`：该方案的景摘要列表，**最多 20 条**（`sceneCount` 仍是景总数，`scenes` 可能比它少），
每景与检索结果同一形状（`id` / `acquiredAt` / `cloud` / `resolution`）—— 要逐景讲就用它，`id` 还能回填 `excludeSceneIds` 换一景。

读数三条硬规矩：

- **覆盖率只能取该方案自己的 `coveragePercent`**。`pool.coveragePercent` 是候选池的，拿它去说某一套，恒得 100%。
- **金额只来自本工具**（`estimatedAmount`）。`pricingComplete=false` 时它是**下界**，对用户要说"≥"。永远不要用单价乘面积自己推。
- `poolAtLimit=true` 时**不要说"这个范围盖不满"** —— 池可能被截断，只是这次没取全。

还要主动带出三件事：

- **池诊断 `pool`** 是"为什么只剩这几景"的唯一解释来源：`candidateCount = usableCount + skippedNoGeometry + skippedNoIntersection + skippedByCloud + skippedByFilter`。
  说"被云量条件筛掉 12 景"（`skippedByCloud`），不要含糊成"条件太严"。
- `budgetCapped=true`：讲清"按这个预算只盖到 X%，要盖满约需 ¥`budgetFullCoverageAmount`"。
- `relaxation.value` 非空 = "把云量放宽到 X% 就能盖满"。为 **null 有两种含义**（池内怎么放宽都盖不满 / 口径上不给建议），**都不是**"这块地盖不满"，不要替它下结论。

## 四、用户改条件时怎么做

推荐工具**每次都自己取候选池**，所以改条件只需重调 `geoclar_recommend_schemes`，**不必重发检索**。一次只改一维，改完把新旧两套放一起对比。
**给了任一条件就转 `custom`**（只给云量这一项也算），返回 `CUSTOM` + 三套同池对照。

| 用户说 | 传什么 |
|---|---|
| "太贵了"、或给出预算 | `budget`；被预算卡住就讲清只盖到多少、盖满要多少 |
| "想更清晰" | `maxGsd` |
| "云量太高" | `maxCloud` |
| "只看某段时间" | `dateFrom` / `dateTo`（`yyyy-MM-dd`；起始不能晚于结束） |
| "只要某个数据集" | `datasetIds`（逗号分隔的数字 ID，取自目录工具） |
| "别要太侧着拍的" | `offNadirMax`（度；`0` = 只要正视） |
| "想要同一天拍的" | `preferConsistent=true` |
| "这一景不要，换一景" | `excludeSceneIds`（逗号分隔，取自方案的 `scenes[].id`） |
| "换一块地方" | 回到第一节重新拿范围；**形状变了要重新体检** |

`excludeSceneIds` **不能单独给** —— 它必须与至少一个条件同时出现，否则会被拒（"换一景"是一次重算，不是干跑）。
用户只说了"换一景"时，先问他最在意哪一维，用那一维当条件一并传。

## 五、调用耗时的量级，以及失败时怎么做

单次检索要并发问多个数据源，**10~90 秒是正常的**。因此：

- **一次超时或失败之后不要连发**。重复调用只会让用户看到一串失败，而且每次都真的把成本再付一遍。正确做法是**缩小范围或收紧条件**（更小的 AOI、更窄的时相、更低的云量上限、指定数据集），或者改走异步那条路。
- 客户端可能有工具调用超时（取决于调用侧配置）。超时意味着**这次没拿到结果**，不意味着没有影像。
- **`geoclar_recommend_schemes` 是整套里最重的一个**（要取池、选景、结算、算金额）。它超时就如实说"方案与金额未取到"，**不要用单价乘面积之类自行推算金额**。

## 六、全部工具都报"无法确定调用者身份"时

这不是检索参数的问题，**不要在检索条件上反复试**。工具入参里没有身份字段，身份由连接器的凭据提供；所有工具同时报这一句，说明**连接器侧的凭据没被接受**（例如凭据值缺少认证方案前缀）或令牌已撤销。此时应报告"连接器凭据需要检查/重新授权"，而不是继续改查询条件。

## 七、结果比预期少时

不要直接说"没有影像"或"只有这么多"。先分清：

- `geoclar_list_datasets` 给的是**平台公开目录**，不代表这个用户被授权的范围；他授权之外的数据集不参与检索；
- 某些**数据源可能整条不可用**（凭据未配置、被停用、供应商故障）。这类源不会报错给用户，只会让结果里少掉它的部分。

所以如实表述为"在你可见的数据集范围内命中 N 景；部分数据源当前不可用，可能少了一部分"，而不是断言世界上只有这些影像。

## 八、助手侧做不到的事

下面这些门户页面能做的，**当前没有对应的工具**，不要承诺、也不要变通着凑：

- **导出 SHP / KMZ** —— 产物没有回传通道，引导用户去门户「影像检索」页选中后导出。
- **下单**（存档下单 / 编程下单）—— 本层只到"给出方案与金额"。
- **地名解析** —— 见第一节，只能近似 + 确认。
- **单景快视图、单景单价** —— 结果里每景只给标识、成像时间、云量、分辨率四个标量。
- **失败批次就地重试** —— 门户页面上能重试某个失败批次，本层没有这个工具：如实报告失败批次，建议用户去门户页处理。

## 九、汇报口径

- **出参里有什么就说什么。** 可用性、时相、分辨率、覆盖率、云量来自检索结果；**金额只来自 `geoclar_recommend_schemes`** —— 没调到它、或它超时，就不要出现金额。
- 几何只给标量摘要（面积、覆盖比、中心点），不要把完整坐标串贴给用户。
- 结果里的标识是平台侧的不透明句柄，按它再次查询时工具会自行校验归属；不要试图拼接或猜测其他标识。
