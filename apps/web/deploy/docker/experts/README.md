# deploy/docker/experts — GeoClar 专家导入包

11 个专家的 `workdsh-expert` 导入包（schemaVersion 1），按三层结构组织：**平台能力**（怎么把数据拿到手）、**通用能力**（数据怎么算、怎么分析、怎么呈现）、**领域**（某个行业该怎么做）。

| # | 专家 | 层 | categoryId |
|---|---|---|---|
| 1 | 卫星任务规划顾问 | 平台能力 | `acquisition` |
| 2 | 卫星影像采购顾问 | 平台能力 | `acquisition` |
| 3 | 遥感影像解译分析师 | 通用能力 | `geospatial` |
| 4 | GIS 空间分析师 | 通用能力 | `geospatial` |
| 5 | 地图设计与可视化专家 | 通用能力 | `presentation` |
| 6 | 地理数据治理专家 | 通用能力 | `data` |
| 7 | 农业遥感专家 | 领域 | `agriculture` |
| 8 | 洪涝与水体监测专家 | 领域 | `disaster` |
| 9 | 城市遥感专家 | 领域 | `urban` |
| 10 | 海事与海洋监测专家 | 领域 | `maritime` |
| 11 | 灾害应急遥感专家 | 领域 | `disaster` |

分层关系：领域专家在需要数据时调用平台能力层，在需要方法时调用通用能力层。例如「农业遥感专家」判断需要 NDVI 时序后，会调「卫星影像采购顾问」拿数据、「遥感影像解译分析师」算指数、「地图设计与可视化专家」出图。

## 为什么是导入包，而不是内置模板

两个原因，都是机制决定的：

1. **内置模板是所有部署共享的。** `templates.ts` 在 `workdsh-plugin-experts` 包里，改了会随发行版发给每一个 WorkDSH 部署——把某个产品的领域专家塞进去不合适。
2. **播种只在专家目录为空时执行一次**（`experts-manager.ts:380`：`if (this.expertsTable().size > 0) return;`）。已经播过默认专家的部署，往模板里加新的**也不会出现**，必须先清空 `storages/workdsh_experts`。

导入包是官方支持的对外格式：带 manifest 摘要校验，导入时人工预览确认。代价是**每套部署要导入一次**。

## 导入

在 WorkDSH 界面进入「专家 · 技能 · 连接器」→「我的专家」→ 导入，选本目录下的 `.expert.zip`，预览整套内容后确认发布。逐个导入（11 个）。

导入不授予权限、不运行脚本、不安装依赖。

## 重新生成

改了专家定义（本目录的 `build-experts.mjs`）之后：

```sh
cd apps/web
node deploy/docker/experts/build-experts.mjs
```

脚本调用插件自己的 `buildExport` 产出包，并用导入方的 `preflightPackage` 逐个自校验——**不要手工改 zip**，包内 manifest 的 sha256 对不上会被导入器拒绝。

## 专家团（3 个）

| 团 | 交付什么 | 成员 | 阶段 DAG |
|---|---|---|---|
| **遥感监测团队** | 区域监测成果（数据来源与口径、方法与参数、精度与局限、成果图） | 采购 · 解译 · 数据治理 · 制图 | 取数(采购) → 分析(解译，**复核=数据治理**) → 出图(制图) |
| **卫星拍摄团队** | 可下单的拍摄方案（可行性、成本对照、待确认项） | GIS · 采购 · 解译 | 范围(GIS) → 成本(采购) ∥ 可解译性(解译) |
| **应急响应团队** | 应急成果图（含时相、覆盖、置信度标注）+ 待验证清单 | 洪涝 · 制图 · 解译 | 版面(制图) ∥ 方法(洪涝) → 复核(解译) |

设计要点：

- **reviewer 只用在交叉风险上**。监测团里让数据治理复核解译产物，是因为"多源一致性、时相归一"正是解译最容易出错又最难自查的地方；不用在流程装饰上。
- **能并行的别串**。应急团的图面准备不依赖数据，先跑起来——数据一到就填，这是应急场景唯一值得优化的关键路径。
- **团名用中文后缀，不用 "XXX Team"**。业内成熟产品的做法是用后缀表达团队性格（团队 / 专家团 / 研究团队 / 工坊 / 咨询团），而不是中英混排。

### 机制上的两条硬约束（`definition.ts` 会校验）

1. **主理人不算成员**。`worker` / `reviewer` 必须引用 `team.members` 里的 key；主理人自己的主责工作不写进阶段——对应官方那句"空 stages 表示主理人直接处理"。所以阶段的划分逻辑是「**委派给成员的部分**」，不是任务全貌。
2. **成员 key 不能叫 `lead`**，且须匹配 `/^[a-z][a-z0-9-]{0,39}$/`。

另外：**团队名取自主理人定义的 `name`**（root 即 lead），所以每个团都要写自己的主理人定义，成员才是从那 11 个专家里取的内容快照。

### 内容快照不自动更新

成员是**导入时的内容快照**——以后改了单个专家的定义（比如调整 tags），团里的成员**不会跟着变**，必须重新导出团包再导入。这是有意的设计（保证团可复现），但你们要接受这个维护方式。

## 已知局限

- **知识只在提示词里。** 这 11 个包没有附 `references/`。农业、洪涝这类领域专家要给出**可验证的数字**（物候期、提取阈值），需要额外配参考文档——目前靠 `boundaries` 强制它们"没有依据就明说并请求补充"，而不是臆造。
- **平台能力层暂时只能讲方法。** 「卫星任务规划顾问」和「卫星影像采购顾问」要真查数据，依赖 `geoclar-java` 的 `/mcp` 能力层（目前只有 demo）与身份票据端点（未实现）。
- 导入是**验证阶段**的形态。确认内容好用之后，再考虑改成内置（届时需同时处理上面的播种时机问题，以及前门升级判定要纳入 `sourceCommit`，否则同版本重新打包不会被识别为需要重装）。
